## 1. 무엇을 했나

공공데이터포털 일별 시세를 받아 원문 그대로 보존하고 수정주가로 정규화하는 수집기를
`collector/` 에 세웠다. 1,972줄이다. 09-22 데이터 수집 가동이 목표라 코드부터 썼다.

돌려 봤다 — 35 거래일 · 93,636행 · 원문 25.7 MB(gzip 5.8 MB) 를 실제로 받았고,
중단·재개와 무결성 검사가 동작한다.

## 2. 가장 크게 배운 것 — 계산하지 말고 데이터에 물어봐라

S26 까지 나는 수정주가를 **등락률(`fltRt`) 을 누적**해서 만들 생각이었다. 그리고 액면분할
기준가는 `직전 종가 ÷ 분할비율` 로 계산하면 된다고 생각했다.

**둘 다 틀렸다.**

카카오 2021-04-15 (1:5 분할) 을 실제로 받아 보니:

| 계산 방식 | 결과 |
|---|---|
| 558,000 ÷ 5 (내가 하려던 계산) | 111,600 |
| `fltRt` 로 역산 | 111,999.3 |
| **`vs`(전일대비 금액)로 역산** | **112,000** ← 실제 기준가 |

거래소가 정한 기준가는 **112,000** 이다. 호가 단위에 맞춰 조정되기 때문에 단순히 5로
나눈 값이 아니다. 그런데 `vs` 필드에 그 값이 **이미 들어 있었다** — 종가 120,500 에서
전일대비 8,500 을 빼면 정확히 112,000 이다.

즉 **조정계수를 추정할 필요가 애초에 없었다.** 데이터가 알려 주는데 내가 계산하려 했다.

`fltRt` 가 덜 정확한 이유도 명확했다. 소수 **둘째 자리까지만** 온다 — 삼성전자
2026-09-17 은 실제 −0.3945% 인데 `"-.39"` 로 잘린다. 하루 오차가 작아도 1,648일을 곱해
나가면 쌓인다. `vs` 는 정수 원 단위라 자를 것이 없다.

> **교훈**: 도메인 규칙(호가 단위, 기준가 산정)을 내가 재현하려 들면 반드시 어딘가 틀린다.
> 출처가 이미 계산해서 준 값이 있는지부터 찾는다.

## 3. 두 번째 배운 것 — 확인해 줄 두 번째 신호를 찾아라

`vs` 를 믿기로 했지만, 그것 하나만으로는 틀렸을 때 알 방법이 없다.

그런데 같은 응답 안에 **상장주식수(`lstgStCnt`)** 가 있었다. 분할이면 주식 수가 늘어난
배수만큼 가격이 내려가야 한다. 즉 가격 계수 `f` 와 주식수 비율 `q` 를 곱하면 1 이 되어야
한다. 두 값은 서로 독립이다.

79건에 적용해 봤다:

| 분류 | 조건 | 건수 |
|---|---|---:|
| `split` 분할·병합 (두 신호 일치) | `f·q ≈ 1` | 54 |
| `rights` 권리락 (주식수 아직 그대로) | `q ≈ 1`, `f ≠ 1` | 21 |
| `review` 둘 다 어긋남 → 사람이 확인 | | 4 |

**사람이 봐야 할 것이 5% 로 줄었다.** 그리고 이 과정에서 S26 의 열린 질문 하나가 풀렸다 —
"권리락에서도 `vs` 가 통하는가". 씨젠(2021-04-23, 무상증자)·대한제당(04-29)이 정확히
잡혔다. 통한다.

## 4. 세 번째 배운 것 — 안 되는 경우를 찾아야 규격이 완성된다

`review` 4건 중 아이엠텍이 결정적이었다.

```
20210401~07   종가    214   vs 0   거래량 0
20210408      종가  5,350   vs 0   거래량 0   ← 정지인 채로 값만 바뀜
```

**거래정지 구간에서는 `vs` 가 계속 0 이다.** 그러면 "가격이 이어진다" 와 "조정 정보가
없다" 가 구별되지 않는다. 정지 해제일에 가격이 달라져 있으면 그것이 조정 때문인지 실제
등락인지 알 방법이 없다.

이건 고칠 수 있는 버그가 아니라 **데이터의 한계**다. 그래서 자동으로 판단하지 않고
`review` 로 남겨 사람에게 넘기게 했다.

> 잘 되는 사례만 보고 "규격 완성" 이라고 적었으면, 나중에 이 4건이 조용히 틀린 채로
> 백테스트에 들어갔을 것이다.

## 5. 네 번째 배운 것 — 일정을 데이터에 맞춰야지 그 반대가 아니다

원래 계획은 "매일 KST 14:00 에 당일 시세 수집" 이었다. 실측해 보니 **성립하지 않는다.**

2026-09-19(토) 11:00 에 확인한 결과:

| basDt | 요일 | totalCount |
|---|---|---:|
| 20260917 | 목 | 2,870 |
| **20260918** | **금** | **0** ← 거래일인데 없다 |
| 20260913 | 일 | 0 ← 휴장일 |

포털은 당일 시세를 당일에 주지 않는다. 더 곤란한 것은 **휴장일과 "아직 안 올라온 거래일"
이 똑같이 0건**으로 온다는 점이다. 구분해 주지 않는다.

그래서 설계를 바꿨다. 당일을 찍는 대신 **최근 2주를 되돌아보며 빈 날만 채운다.** 그러면
지연이 하루든 이틀이든 알아서 메워지고, **지연의 정확한 길이를 알아낼 필요가 없어진다.**

모르는 값에 기대지 않는 쪽으로 설계를 옮긴 것이 이 결정의 핵심이다.

## 6. 유량 — 4시간 40분 관측이 답이 됐다

S24·S25·S26 이 못 끝낸 숙제였다. 짧은 주기 리셋인지, 24시간 롤링인지, 고정 창인지.

| 시각 (KST) | 남은 유량 |
|---|---:|
| 09-18 14:4x ~ 19:26 | 9,790 → 9,770 (**4시간 40분 무복구**) |
| 09-18 세션 종료 | 9,757 |
| **09-19 11:03** | **9,999** |

앞쪽이 짧은 주기 리셋을 배제하고, 마지막 줄이 24시간 롤링을 배제한다(롤링이라면 09-18
14시 호출분은 아직 24시간이 안 지나 9,757 근처여야 한다). **고정 창이다.**

다만 창이 갈리는 시각은 19:26~11:03 사이로만 좁혀졌다. 그래서 코드는 **그 시각을 알
필요가 없게** 짰다 — 응답 헤더가 주는 남은 횟수만 보고 판단한다.
